# 用排错编号定位资料问答失败

资料问答的 HTTP 请求失败时，页面可以显示服务端返回的排错编号。维护者用它查找同一次请求的诊断日志，不需要把问题正文、知识资料或整份浏览器网络记录复制给别人。

## 页面操作

1. 在「内容任务 → 资料问答」查看失败提示。只有本次失败响应提供了合法的 `X-Request-ID` 时，才显示排错编号。
2. 点击「复制排错编号」。复制内容仅是编号，不包含错误正文、问题、URL、账号、组织或模型配置。浏览器不允许复制时，手动选取只读编号即可。
3. 记录大致发生时间与操作类型，用编号在自己的私有日志中定位，或将这些必要信息交给维护者。不要直接发送整个数据库、请求体、Cookie、凭证或服务日志。
4. 修改问题、参数或知识库后，旧的查询错误和编号会清除；下一次请求失败应使用新的编号。知识库或检索配置初始化失败会单独保留，编辑问题不会隐藏加载故障；重新加载页面或切换初始化范围后重新取得状态。不要把先前请求的错误编号当成当前请求的证据。

正常的证据不足拒答属于业务回答，通常是 HTTP 200，不会因此显示“请求失败”的排错组件。网络连接失败、请求取消或服务端没有合法响应头时，不补造编号，也不从响应正文猜测它。

当前只在资料问答页接入可复制组件，并非所有页面都已提供这个入口。其他页面仍可由维护者查看响应头。UI 编号是排错线索，不是身份凭证、审批结果或内容安全检查。

## 维护者如何核对

服务端生成 32 位小写十六进制请求 ID。前端仅使用失败响应头中的同格式值；响应正文中的同名字段不作为来源。浏览器当前登录的组织或请求上下文变化时，旧请求及错误体读完后的结果都会被丢弃，避免旧组织错误混入新页面。

按 [请求诊断](diagnostics.md)查找相同 `request_id` 的 `http_response`、`http_failed` 或团队边界事件；涉及内容任务时再核对任务与执行尝试。不要只按 HTTP 503 推断任务未受理：用量可能已经受理，结算也可能提交但回执未知，须按 [结算故障说明](usage-finalization-failures.md)先核查。

编号来自当前响应，不证明日志必定已持久化。找不到对应事件时记录缺口，检查所看的服务实例、时间范围和日志保留条件；不能把缺日志解释为零调用、无费用或没有业务副作用。

## 验证边界

请求层单元测试使用模拟 fetch 和 Headers，检查合法/非法编号、正文伪造、网络失败、取消，以及读取错误体期间切换组织。页面验收使用隔离临时服务触发真实 HTTP 错误，比较响应头、页面和私有日志中的编号，并单独验证复制失败与清除状态。

复制成功只证明浏览器写入了那段编号，不证明维护者收到它或完成排错。本功能不会自动上传诊断信息，不打开外部工单，也没有外部通知渠道。
