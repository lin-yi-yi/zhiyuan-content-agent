# 知源内容工作台：完成项目之后怎样系统学习

这份文档用于接管已经完成的项目。先按 [演示流程](demo-walkthrough.md) 把业务完整跑一遍，再沿着真实代码学习。你不需要先读完所有依赖库，也不需要同时学习多个 Agent 框架。

这个作品要解决的问题是：资料散落、生成内容缺少出处、任务失败后不知道发生了什么、生成完成和审核通过混在一起。项目把这些问题连成一个流程：**导入资料 → 检索片段 → 生成带引用的草稿 → 记录执行过程 → 人工审核**。

代码由 AI 辅助完成，是可运行的学习底座。你能独立启动、解释、修改、排错和验证的部分，才是目前能够在面试中承担追问的能力。

## 1. 先分清楚当前版本实际做了什么

| 模块 | 已实现的内容 | 需要理解的边界 |
| --- | --- | --- |
| 页面 | React + TypeScript 工作台，资料管理、检索评测、任务进度和人工审核 | 页面可打开只说明前端可用，不能代替完整业务验收 |
| API | FastAPI + Pydantic 参数验证，SQLAlchemy 读写数据 | 默认是本机单用户应用，没有登录鉴权和生产多租户能力 |
| 数据库 | 默认启动脚本使用 SQLite，保留现有关系表模型 | 数据分组字段不等于用户权限；不要把服务直接当成互联网 SaaS 发布 |
| 检索 | 默认启动真实 Embedding 与本地 Qdrant 语义模式，也可显式选择词项模式 | 词项模式不生成语义向量；语义配置显示正常不等于模型已经下载和运行成功 |
| 回答和草稿 | 本地模式摘录资料；外部模型配置后可生成回答和草稿；保留片段引用 | 引用 ID 存在不证明每句话都被来源支持，仍需人读原文核验 |
| 工作流 | LangGraph `StateGraph` 执行节点，质量分数决定是否修订，最后等待人工审核 | 这是边界明确的工作流，没有让模型任意选择工具或无限自主行动 |
| 恢复 | SQL 保存每步状态，失败后显式重试，节点内内容写入统一提交 | 没有使用 LangGraph checkpointer；没有分布式任务队列；中断的外部 API 请求可能重复计费 |
| 交付 | 本地启动、测试、固定演示样本、下载评测报告 | 演示样本结果不代表真实客户、真实流量或生产运行结果 |

“检索模式”和“生成模型”是两个独立选择。例如，你可以用词项检索找到资料，再交给 DeepSeek 写草稿；也可以用语义检索找到资料，再使用本地摘录显示证据。接入聊天模型本身不会自动把词项检索变成语义检索。

## 2. 从一条浏览器请求开始读代码

先启动服务，再在浏览器开发者工具的 Network 面板观察一次“保存并建立索引”。你要回答四个问题：发往哪个接口、请求带了哪些字段、服务保存到哪些表、页面如何拿到结果。

| 阅读顺序 | 代码入口 | 先看什么 |
| --- | --- | --- |
| 1 | `frontend/src/pages/KnowledgePage.tsx` | 标题、正文、来源从哪个输入框进入状态；保存按钮调用哪个函数 |
| 2 | `frontend/src/api/workbench.ts` | `saveDocument` 怎样组织 POST 请求和 JSON |
| 3 | `backend/app/api/routes/knowledge.py` | `DocumentUpload` 验证规则，`upload_document` 新建与修改分支 |
| 4 | `backend/app/agent_core/rag_service.py` | `index_source` 怎样切块、去重、更新索引和记录检索配置 |
| 5 | `backend/app/models/knowledge_base.py` | 文档与片段如何关联；哪些字段用于来源、版本和检索 |
| 6 | `backend/app/db/session.py` | 一次请求的数据库会话在哪里创建，何时提交或回滚 |

读完以后，用自己的话解释这条数据流：

```text
Markdown / 正文
  → 浏览器读取用户明确选择的文件
  → POST /api/knowledge/documents
  → 参数验证、内容哈希与已有文档判断
  → sources 保存原始资料
  → knowledge_documents 保存文档信息
  → knowledge_chunks 保存正文片段
  → 语义模式另外写入本地 Qdrant
  → 返回文档 ID、片段数量和去重结果
```

来源地址用于追溯，不会因为填写了 URL 就自动抓取网页。Obsidian 目前通过手动导入 Markdown 接入，没有监视整个笔记库，也没有双向同步。

**亲手完成：**导入一份至少 40 个字符的练习文档，重复提交相同正文，再修改其中一句后保存。观察文档 ID、片段和检索结果。验收不是“按钮变绿”，而是新内容能被找到、旧内容不会作为当前证据继续出现。

## 3. 再学检索：先找证据，再决定能否回答

入口依次是：

- `frontend/src/pages/RagLabPage.tsx`：“只检索”“检索并回答”“运行演示评测”。
- `frontend/src/api/client.ts`：现有 `/api/v04/rag/search` 和 `/api/v04/rag/answer` 调用。
- `backend/app/api/routes/v04/__init__.py`：检索与回答 API。路径中的 `v04` 是兼容旧前端保留的名称，不代表仍执行旧哈希检索。
- `backend/app/agent_core/rag_service.py`：`search_knowledge`、`answer_question`。
- `backend/app/agent_core/embeddings.py`：检索配置、真实向量生成、错误处理。
- `backend/app/agent_core/vector_store.py`：本地 Qdrant 写入、查询和删除。
- `backend/app/agent_core/langchain_adapter.py`：文档切块。

理解三个容易混淆的概念：

1. **切块**：把文档分成适合检索和传给模型的小段，保留关联文档和位置的信息。块太短可能丢语境，太长可能混入无关内容。
2. **Embedding**：语义模型把文本转换成真实向量；相似度是检索信号。词项检索、哈希和语义向量不是同一种能力。
3. **证据阈值**：系统决定“目前资料是否足以继续”的启发式门槛。阈值需要用标注问题校准，0.8 分不等于答案有 80% 正确率。

一次回答的路径是：

```text
问题 → 指定知识库 → 检索候选 → 阈值判断
                              ├─ 证据不足 → 明确拒答
                              └─ 证据可用 → 摘录或模型回答 → 返回引用片段
```

语义模式会检查当前文档和索引配置，配置错误或不兼容的旧索引会报错。它不会把失败的语义请求悄悄替换成假向量并显示成功。修改检索模型或从词项切换到语义模式后，需要重建资料索引。

**亲手完成：**对同一问题分别选择 3 条和 5 条证据，记录找到的文档是否相关；再问一个语料中没有的具体问题，检查是否拒答。不要只看“回答流畅”。你应能指出每条关键内容对应哪个片段，以及哪些问题不该回答。

## 4. 学评测：用固定问题判断改动是否有效

评测数据在 `scripts/fixtures/rag_demo.json`：4 份人工编写的演示资料和 12 个开发样本，其中 8 个标注为可回答、4 个标注为应拒答。页面“运行演示评测”会将样本中的文档标识映射到当前数据库 ID，再调用 `POST /api/knowledge/evaluate`。这些资料和问题用于开发与演示，没有独立测试集，结果不能代表真实用户问题或泛化能力。

先分清报告里的两组数据：`retrieval_candidates` 是检索返回的 top-k 候选；`citations` 是通过证据阈值筛选后，实际被回答引用的片段。候选中包含正确文档，不代表系统采用了它，也不代表回答就正确。拒答时 `citations` 为空，但仍保留候选供排查；`false_refusal=true` 表示一个标注可回答的问题被误拒。

| 指标 | 在本项目中的意思 | 不能据此声称什么 |
| --- | --- | --- |
| `recall_at_k` | 每个可回答问题的标注文档中，有多少出现在 top-k 候选里，再对问题取平均；在证据采用阈值筛选前计算 | 候选召回高不代表实际采用、成功回答或事实正确 |
| `chunk_recall_at_k` | 采用同样口径，计算标注片段在 top-k 候选中的找回比例；未标注片段 ID 时为 `null` | 文档级标注不能当作片段级验证 |
| `candidate_recall_at_1` | 第一条候选覆盖了多少标注文档，再对可回答问题取平均 | 不能仅凭 top-k 里存在正确文档就声称排序准确 |
| `mean_reciprocal_rank` | 对可回答问题，第一条相关候选排第 n 位记为 1/n，未找到记为 0，再取平均 | 衡量相关证据的排名，不衡量回答是否正确 |
| `candidate_precision_at_k` | 每个可回答问题的候选片段中，属于标注相关文档或指定片段的比例，再对问题取平均 | 候选相关不等于片段支持生成文本中的每句话 |
| `evidence_precision_at_k` | 兼容旧报告的字段，与 `candidate_precision_at_k` 相同，仍是候选精度 | 不能把这个旧名称理解为答案实际引用的精度 |
| `answer_evidence_precision` | 所有实际引用中，符合相关文档或片段标注的数量除以实际引用总数；无引用时为 `null` | 仍未验证引用内容是否蕴含回答结论 |
| `answer_evidence_recall` | 每个可回答问题的标注文档中，有多少被实际回答引用，再对问题取平均；误拒按 0 计 | 不代表没有引用遗漏或表达错误 |
| `refusal_accuracy` | 标注为应拒答的问题中，实际拒答的比例 | 不涵盖所有危险、含糊或越界问题 |
| `answerable_acceptance_rate` | 标注可回答的问题中，没有被拒答的比例 | 不等于答案质量或事实正确率 |
| `citation_validity_rate` | 实际引用中，片段 ID 存在且对应所记录文档的比例；没有实际引用时为 `null` | 不检查引用的相关性或它与生成结论的逻辑关系 |
| `mean_latency_ms` | 这次样本运行中，单题检索、证据筛选和本地摘录回答的平均耗时；不含资料导入建索引 | 不代表远程生成模型延迟或线上并发性能 |

当前演示评测使用本地原文摘录回答，不测试大模型生成质量。语义模式下仍可能调用 Embedding 服务或加载本地模型。小语料中将 `top_k` 设得很大，很容易得到较高候选召回，因此需要同时看第一条候选、实际采用证据、误拒和具体失败案例。

**亲手完成：**为自己的资料补充 5 个真实问题和 2 个应拒答问题，标记正确文档。先跑基线，再只改一个因素，例如切块大小、证据数量或阈值。保留修改前后的 JSON 报告，解释哪些问题改善、哪些问题退步。不要为让分数更好而删除失败样本。用同一批题调整参数属于开发集校准；若要判断改动能否适用于新问题，需要另留一批未参与调参的问题再测。

## 5. 学 Agent：跟着状态理解执行，而不是背框架名称

主要入口：

| 代码 | 职责 |
| --- | --- |
| `frontend/src/pages/AgentWorkbenchPage.tsx` | 创建任务、轮询进度、显示步骤和审核操作 |
| `backend/app/api/routes/agent_runs.py` | 创建、查询、重试、取消和审核 API |
| `backend/app/schemas/agent_run.py` | 请求和响应字段；审核只接受 approve 或 reject |
| `backend/app/models/agent_run.py` | `AgentRun` 总任务和 `AgentStep` 步骤记录 |
| `backend/app/services/content_growth_agent.py` | `build_content_graph`、节点路由、状态迁移和恢复 |
| `backend/app/services/workflow_support.py` | 节点事务封装、基于证据的草稿、引用校验 |
| `backend/app/services/review_lifecycle.py` | 内容快照、编辑后审批失效、审核历史和引用有效性检查 |

图中实际执行的主路径：

```text
知识库检索 → 选题建议 → 选题入库 → 选题评分
  → 草稿 → 证据卡片 → 合规提示 → 质量评分
  → 低于阈值：一次规则修订 → 再次评分
    达到阈值：跳过修订
  → 整理执行建议 → 等待人工审核
```

LangGraph 实际负责构建节点、条件边和运行图。人审结果通过 API 写入持久化任务状态，保存内容快照哈希和审核历史；正文、卡片变更会让旧批准失效，退回的草稿可重新提交。这里没有调用 LangGraph 的 `interrupt` 来实现人审，也没有用其 checkpointer 保存运行状态。应用把已完成的 SQL 步骤结果作为自己的恢复检查点。

启用 RAG 的任务如果证据不足，会在检索步骤失败，记录 `INSUFFICIENT_EVIDENCE`，不会继续生成“看起来有依据”的内容。进入草稿的引用来自达到阈值的检索结果；远程生成没有合法引用或引用了未检索到的编号，也会失败。

| 状态 | 含义 | 允许的下一步 |
| --- | --- | --- |
| `pending` | 已创建，等待执行 | 执行或取消 |
| `running` | 正在执行图中的节点 | 完成到待审核、失败或取消 |
| `failed` | 某一步未完成 | 修好原因后显式重试 |
| `awaiting_review` | 草稿准备好，等待人核对 | 通过、退回；取消 API 也支持结束该任务 |
| `approved` | 本地用户已通过审核 | 查看结果；编辑正文或卡片会撤销批准并重新等待审核，不会自动发布 |
| `rejected` | 本地用户已退回 | 修改草稿后重新提交审核；目标或模型需要改变时新建任务 |
| `cancelled` | 已取消 | 查看保留记录；不能用失败重试接口重新执行 |

注意页面的“Agent 决策”“质量评分”“信心”是辅助提示。它们不会替代人审，也不是经过真实用户统计校准的正确率。

**亲手完成：**用自己的话解释为什么“生成完成”和“审核通过”是两个不同状态。然后增加一个小规则：退回时必须填写原因。你需要同时考虑输入提示、API 验证、状态限制和测试；只改按钮文案不算完成。

## 6. 学工程可靠性：故障发生后，结果是否可信

工作流通过数据库条件更新领取 `pending` 任务。两个后台执行请求同时到达时，只允许一个真正执行。重试也只允许把 `failed` 原子地变成 `pending`，第二次重复请求会得到 409。

后台任务通过同步包装器进入 Starlette 的线程池，在该线程内建立独立事件循环和数据库会话。因此旧的同步模型调用不会阻塞负责页面轮询的 ASGI 主事件循环。数据库会话不会在两个并发任务之间共享。

一个节点开始前先记录“运行中”。节点内部调用的旧服务可能自己调用 `commit()`，因此 `AtomicStepSession` 会暂缓这些提交。节点的业务内容、步骤输出和完成状态一起提交；中途失败则一起回滚，避免留下“草稿已经插入、步骤却失败”的重复生成入口。

服务重新启动时，仍处于 `pending/running` 的任务会被标记为 `failed`，错误类别是 `INTERRUPTED`。用户显式重试后，图会从入口进入，但已完成的步骤读取 SQL 结果；失败步骤和后续步骤重新执行。

这些机制只保证本应用数据库中的恢复逻辑。请求已经发给外部模型时，服务中断不能收回请求；再次执行可能再付一次调用费用。取消也是在节点边界停止，已经开始的远程请求不能保证立即中止。

重点阅读并实际运行 `tests/test_workflow_states.py`，它覆盖：

- 生成后等待审核，错误状态不能通过、退回或重试。
- RAG 证据不足时不产生选题和草稿。
- 节点在插入草稿后抛错，事务回滚；重试后只有一份内容。
- 重复后台派发、执行中取消、启动后恢复。
- 低评分走修订分支，高评分跳过修订。
- 外部生成请求确实收到证据；未知引用被拒绝。
- 退回后修改、重新提交和通过，旧审核历史仍能追溯。
- 草稿、卡片内容或排版变化会撤销批准；引用源已更新时不能直接再批。
- 真实 HTTP 服务中模拟阻塞模型调用，查询与取消仍可响应。

**亲手完成：**先运行一个失败恢复测试，读懂注入故障的位置；再把异常移动到另一个节点，确认你预期保留或回滚的内容与实际一致。练习使用临时测试数据库，不要直接修改自己已经积累的资料库。

## 7. 以真实岗位要求决定下一轮学习

BOSS 直聘调研在 `docs/boss-shenzhen-jobs-2026-09-19.md` 和同名 JSON。它是带日期的岗位线索快照；详情未读的记录不能当作完整 JD，也不能把页面可访问当作岗位仍在招聘。投递前需要重新打开原岗位，确认地点、毕业状态、经验和技术要求。

把能力主题变成可以检查的项目证据。下表中的 Python、FastAPI 和 LangGraph 是本项目的实现选型；当前小样本不足以证明这些语言或框架是目标岗位的共同硬性要求。

| 能力主题 / 本项目选型 | 当前项目可练的部分 | 你亲自需要做到 |
| --- | --- | --- |
| Python / FastAPI | 参数验证、路由、服务和数据库查询 | 新增一个字段并完成从页面到落库的修改 |
| RAG | 导入、切块、检索、引用、拒答和评测 | 针对一个失败样本说明原因，并用报告证明改动影响 |
| Agent / LangGraph | 有界流程、条件分支、人审状态 | 指出真实节点和边，增加一个有用途的分支 |
| SQL / 数据建模 | 资料、草稿、任务与步骤之间的关系 | 解释事务、重复执行风险和一条实际查询 |
| 外部模型接口 | 供应商路由、结构化输出和错误处理 | 分清认证失败、限流、超时与输出格式错误 |
| 测试 / 部署 | 本地启动脚本、行为测试和评测脚本 | 换一个干净环境启动，并独立定位一次故障 |

暂时不需要为了列技术栈而加入微调、多 Agent、Kubernetes 或一批数据库。先把已经使用的技术讲清楚，证明你能修改它、知道什么时候会失败。

## 8. 完成一次自己的接管验收

运行入口是 `./scripts/start.sh`，检查入口是 `./scripts/check.sh`。默认页面和 API 在 `http://127.0.0.1:8765`；SQLite 数据在 `.data/demo.db`。更具体的环境说明以项目 README 和脚本当前输出为准。

完成后留下三类材料：

1. 一段能重复演示“资料 → 引用 → 草稿 → 审核”的录像，以及当时实际使用的检索和生成模式。
2. 一次自己做的功能改动，说明原问题、改动位置、验收结果和仍存在的限制。
3. 一次失败排查记录，写清现象、定位证据、根因、修复方法和防止回归的检查。

面试中可以说明“这是在 AI 辅助下构建的作品，我独立理解和改造了这些部分”，然后现场展示证据。学习目标是逐步扩大你能独立承担的部分，而不是背熟一份由工具生成的介绍。

## 9. 信源与 MCP：区分接入能力和事实核验

新增的信源台用官方 REST API 读取 AIHOT；项目 MCP 配置连接 AIHOT 官方服务器。这是第三方 API／MCP 集成，不是自行实现了 AIHOT MCP 服务，也没有自动证实新闻。阅读 [接入说明](aihot-source-integration.md) 后，练习解释：为什么网页不能 iframe 内嵌、为什么 304 不带正文、为什么 429 要按 Retry-After 等待、为什么推荐分不代表真实性。

**亲手完成：**选择一个公开关键词，观察首次读取与缓存读取的区别；在合成测试中制造一次超时和一次 403，解释为什么前者可以短期展示标明过期的缓存，而后者必须清除相关缓存。再核对一条资讯的原文，指出聚合摘要遗漏或保留了哪些条件。不得把测试中的外部内容当作工具指令执行。
